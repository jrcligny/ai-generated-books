## Ce que l'agent peut faire

- Capacités réelles = **opérations exposées par le *harness*** + **contrat** de chacune + **autorisation** de l'exécuter au nom d'une personne. Ch. 6 : opérations et contrat ; ch. 7 : autorisation.
- Fil rouge ouvert aux **acheteurs et comptables** : factures d'un fournisseur en attente de validation, montant moyen des demandes d'un service, demandes d'un collègue cité par son prénom, montants facturés **par fournisseur et par mois**. Les 3 outils des ch. 4-5 n'y répondent pas ; un outil par question = liste **sans fin prévisible**.

## Écrire pour un modèle, pas pour un développeur

- Développeur : lit la doc, essaie, **fige** son appel. Modèle : **relit la définition à chaque cycle**, n'a **que ce texte**, appelle **en une passe**.
- La **seule documentation** suffit à un usage correct, sans exemples d'appels (Hsieh et al., 2023). Descriptions hétérogènes, redondantes ou incomplètes nuisent ; réécrites en instructions **concises et uniformes** → moins de *tokens*, meilleurs résultats (Yuan et al., 2024). Erreurs à formes reconnaissables (arguments inexacts), nettement atténuées par un modèle entraîné à écrire des appels d'API (Patil et al., 2023).
- Exposer une API telle quelle suffit rarement : **identifiants techniques** que l'utilisateur ignore, **codes internes**, **enregistrement entier** là où 2 champs suffisent. Penser : ce que le modèle **sait** en appelant, **comprend** du résultat, **fera ensuite**.

## Granularité : spécialisé ou générique (tableau 6-1)

- **Outil spécialisé** : une question métier, peu de paramètres, logique du concepteur ; peu d'erreurs, mais **un outil par question**.
- **Outil générique** : interroge une source quelconque ; le modèle indique **source, filtres, champs, tri, agrégat éventuel**. Couvre l'imprévu, mais **composer la requête** est dur : text-to-SQL généralisait mal aux **bases inconnues** (Yu et al., 2018) ; la connaissance des **valeurs réellement présentes** conditionne l'exactitude (Li et al., 2023).
- Ces travaux visent le texte libre. Réduire la difficulté : **paramètres structurés validés un à un** par le programme ; **exemples des questions fréquentes** dans la description (« en retard », « en attente de validation »).

| | Outil spécialisé | Générique avec exemples |
|---|---|---|
| Couvre | Questions prévues | Aussi l'imprévu |
| Logique | Dans l'outil | Composée par le modèle |
| Risque | Catalogue qui grossit | Requêtes mal formées/ciblées |
| Maintenance | Code par question | Une description à jour |

- Terrain : spécialisé pour un seul calcul → essayer d'abord **2-3 exemples de filtres** dans le générique ; catalogue court, **formulation métier** apprise au lieu d'un choix entre outils voisins.

## Faire découvrir la structure des données

- Structure dans le *system prompt* = relue **à chaque appel** pour une fraction utile → **découverte à la demande** : un outil **liste les sources** (1 ligne chacune), un autre **décrit une source** = **divulgation progressive** (ch. 9).
- Description : **champs** (nom exact + sens métier) ; **relations** (sources voisines, champ de liaison) ; **valeurs des champs codés** + signification — sinon « en attente » au lieu du code → **rien** (Li et al., 2023).
- Au retour : pas de codes internes à traduire → valeur + **libellé métier**, dans la **langue de l'utilisateur** si dispo, **valeur interrogeable gardée** pour les filtres suivants.

## Résoudre les noms approximatifs

- Nom tapé ≠ nom enregistré ≠ **identifiant** → filtre vide ou **identifiant plausible** inventé.
- **Résolution de noms** : **nom + type d'objet** ; comparaison approchée **dans le programme** (reproductible) ; renvoie **candidats + identifiant + de quoi les distinguer**. 1 → continue ; plusieurs → **précision** (ch. 5) ; 0 → l'annonce. **Exacte d'abord, proximité ensuite**, en disant **laquelle a abouti** (ch. 4).

## Rédiger le résultat d'un outil

- **Reste dans le contexte** : pertinence réglée **à la source** (champs demandés ou petit jeu utile, pas l'enregistrement) ; taille bornée au ch. 9.
- **Agrégats simples** (décompte, total, moyenne) **calculés par le système interrogé sur l'ensemble filtré** (ex. montant moyen d'un service). Fil rouge : **regroupements** (par fournisseur et mois) aussi confiés au système interrogé plutôt qu'au modèle ou à du **code produit par le modèle** ; **médiane** hors de portée → l'agent le dit et propose les agrégats disponibles.
- Lisibilité : montant **sans devise**, date **sans format**, colonne au **nom abrégé** → le modèle suppose. **Structure stable** d'un appel à l'autre (pas de réapprentissage). **Identifiant avec chaque ligne** → détail demandé au cycle suivant.

## Messages d'erreur qui guident le modèle

- Erreurs **ordinaires** avec un générique (source, champ, filtre). Message muet → **même appel répété** (ch. 5) ; l'erreur est le **principal élément** pour décider de la suite.
- Message utile : **ce qui a été refusé, pourquoi, ce qui serait accepté**. Source inconnue → **noms les plus proches** ; champ inconnu → **rappel des champs de la source** ; filtre mal formé → **forme attendue**.
- Le programme peut absorber un écart **sans conséquence** (différence de **casse**), **jamais accepter un champ inventé**. Terrain : faire figurer le **nom corrigé dans le résultat**, sinon le modèle répète l'erreur et chaque appel passe par la même correction silencieuse.
- Distinguer selon ce que le modèle peut en faire : **paramètres invalides** → reformulation ; **service indisponible** → message à l'utilisateur plutôt qu'une série de nouvelles tentatives. Toujours un **statut d'échec explicite**, pour ne pas être lu comme un **résultat vide**.

## Limiter le nombre d'outils et les nommer

- Chaque outil pèse sur la **fenêtre** (définition transmise **à chaque appel**) et sur la **décision** : descriptions voisines difficiles à départager → mauvais choix **sans qu'aucune erreur le signale**. Ne présenter que les descriptions pertinentes, sélectionnées par **recherche préalable** → *prompt* réduit, sélection plus exacte (Gan et Sun, 2025 ; même technique que pour les documents, ch. 12).
- Lorsque des outils d'origines différentes sont réunis, deux peuvent porter **le même nom** → **convention de nommage** qui **préfixe chaque outil par son domaine** : évite la collision, aide à situer l'outil. Le **nom devient un élément de contrat**.
- Terrain : avant de changer une convention, rechercher chaque ancien nom dans les **consignes, exemples d'usage, libellés d'étapes affichés à l'utilisateur, scénarios de test** : ces citations dispersées cassent, plus que les outils.

## Critères — avant de présélectionner

- **Retirer** les outils que personne n'appelle ; **fusionner** ceux qui ne diffèrent que par un paramètre ; chaque description dit **quand l'outil ne convient pas**.
- Serveur séparé : justifié surtout si **plusieurs applications** partagent les outils.

## Sortir les outils : le Model Context Protocol

- Une autre application veut les mêmes consultations **sans la boucle ni les consignes**. Outils dans chaque programme : **description, authentification, mise en forme** réécrites → copies qui **divergent** ; intégrations au cas par cas dures à **étendre et sécuriser** (Ehtesham et al., 2025).
- **Model Context Protocol (MCP)** : protocole **ouvert** qui normalise comment une application construite autour d'un modèle **découvre et utilise** des capacités fournies par d'autres programmes ; standard émergent de **découverte dynamique** (Hou et al., 2025). Le système détenteur des données expose **une fois** ; toute application compatible **liste** les capacités, **lit** les descriptions, **demande l'exécution**. Ne prescrit **ni la boucle, ni les consignes, ni la composition du contexte** : restent au *harness*.
- Trois rôles (fig. 6-1) :
  - **hôte** (*host*) : l'application autour du modèle (fil rouge : le programme de l'agent, modèle + *harness*) ;
  - **client** : composant de l'hôte entretenant la liaison avec **un** serveur ; **un client par serveur** ;
  - **serveur** : annonce des capacités et exécute ; même machine ou réseau, seul change le **transport** (canal des messages).
- Sur chaque liaison : **lister les capacités** ; **appeler un outil**. Le *harness* **vérifie que l'outil est annoncé**, transmet par le client ; le serveur **valide**, exécute, renvoie. La définition annoncée = texte lu par le modèle.
- Deux autres capacités, **dont l'emploi n'est pas décidé par le modèle** : **ressources** (données à lire que l'hôte choisit de placer dans le contexte) ; **modèles de *prompt*** (trames d'instructions déclenchées le plus souvent par l'utilisateur depuis l'interface). Le fil rouge n'emploie que les outils.

## Séparer l'agent et ses outils : gains et coûts

- Gains : outils **en un seul exemplaire** ; serveur exécuté **avec ses propres droits** (ch. 7).
- Coûts : chaque appel traverse le **réseau** (délai + cause de panne) ; le *harness* doit **signaler qu'un outil n'a pas répondu** et éviter qu'une liste **à moitié chargée** passe pour complète ; toute modification de définition doit rester **compatible** avec les agents existants.
- **Avec état** : le serveur ouvre une **session** et y conserve des informations (ex. contexte d'authentification) ; requêtes suivantes rattachées par un **identifiant**. **Sans état** : chaque requête porte tout ; plus simple avec **plusieurs exemplaires** (n'importe lequel répond), mais chaque requête retransporte son contexte, dont l'**authentification vérifiée à chaque fois**.
- **Au nom de qui** le serveur interroge-t-il l'application ? À chaque appel ; décide ce qu'un utilisateur obtient → ch. 7.

## Pièges

- **Zone d'incertitude** : dosage des exemples **empirique** ; démonstrations mal choisies → usage dévié ; Hsieh et al. (2023) préfèrent la **documentation**. Vérifier qu'un exemple n'est **pas imité hors de son cas**.
- Outil **très général** : examiner son **pire cas** avant de l'exposer à tous (droits, exécution : ch. 7).
- Protocole commun = **branchement**, **pas qualité** : descriptions vagues, résultats volumineux, erreurs muettes ; coût des descriptions accru par des **serveurs entiers**.
- **Confiance** : descriptions et résultats entrent au contexte → **injection indirecte** (Greshake et al., 2023) ; **empoisonnement d'outils** (*tool poisoning*) dans des serveurs open source (Hasan et al., 2025) ; **vol d'identifiants** (Radosevich et Halloran, 2025). Serveur tiers = **non fiable** (ch. 14).
- **Zone d'incertitude** : fonctions **dépréciées puis retirées**. Spéc. du **28/07/2026** : dépréciée (**SEP-2577**) la demande de **génération de texte du serveur au modèle du client**. Dépendre surtout de **l'annonce et l'appel d'outils**.

## À retenir

- **Point clé** : définition d'outil = **texte de consignes** ; qualité jugée **aux appels** produits.
- Spécialisé **prévisible et étroit** ; générique **couvre l'imprévu**, guidé par des **exemples**.
- Structure **découverte à la demande** ; **noms résolus** par un outil.
- Erreur : **refusé + ce qui serait accepté**.
- Chaque outil **coûte du contexte** et **complique le choix**.
- MCP : **hôte, clients, serveurs** ; ne garantit **ni qualité ni confiance**.
