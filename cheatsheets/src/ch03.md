## Le fil rouge

- Appli de gestion (fictive) : **commandes**, **achats**, **factures** ; utilisateurs de métier (chargés de clientèle, acheteurs, comptables) qui ne connaissent pas tous les écrans. **Première demande** : savoir **où en est une commande**. Évolue à chaque chapitre.
- Départ : le modèle prolonge des *tokens*, **ne conserve pas** les messages, **ignore les données** de l'application.

## De la complétion au dialogue : les rôles

- Le modèle prolonge un texte ; rien n'y prévoit d'alternance. Le **dialogue est une convention** ajoutée par-dessus : séquence structurée en **messages**, chacun attribué à un **rôle**.
  - **Système** : consignes du concepteur. **Utilisateur** : ce que la personne a écrit. **Assistant** : ce que le modèle a répondu.
- Transcription : message système → alternance utilisateur/assistant → **se termine par un message utilisateur** ; le modèle écrit le message d'assistant manquant. Frontières marquées par des **_tokens_ spéciaux** réservés.
- Modèles de dialogue : pré-entraînés puis **ajustés** sur consignes + réponses, avec **jugements humains** (Ouyang et al., 2022). **Hiérarchie** apprise (Wallace et al., 2024) : concepteur > utilisateur > contenu de tiers.

## Le *system prompt* : consignes du concepteur

- ***System prompt*** (message système) : texte placé **en tête de chaque conversation** pour orienter le comportement. Non affiché, mais le modèle peut le **restituer** → considérez-le **lisible par l'utilisateur**, **aucun secret**.
- Quatre points ; exemple 3-1 (bibliothèques municipales), un paragraphe par point :
  - **Mission** (qui, contexte, public) : *« Tu es l'assistant en ligne du réseau des bibliothèques municipales. Tu aides les usagers inscrits à trouver un livre et à suivre leurs prêts. »*
  - **Périmètre** (sujets traités / à décliner) : *« Tu réponds aux questions sur le catalogue, les prêts, les réservations et les horaires. Pour toute autre demande, indique que tu ne peux pas aider et oriente l'usager vers l'accueil de sa bibliothèque. »*
  - **Expression** (registre, longueur, langue) : *« Réponds en deux ou trois phrases, dans la langue de l'usager, sur un ton cordial. »*
  - **Règles** (toujours / jamais) : *« N'affirme jamais qu'un livre est disponible ou qu'un prêt est en cours sans l'avoir vérifié dans une source. Ne donne aucune information sur le compte d'un autre usager. »*
- Le modèle **donne du poids** aux consignes sans en **assurer le respect** à chaque exécution → une règle **jamais enfreignable** exige un **contrôle dans le programme** (répartition : ch. 13, tableau 13-1).
- **Sur le terrain** : **versionnez** le *system prompt* comme du code et notez avec chaque modification **le problème qu'elle corrigeait** (sinon consignes ajoutées en urgence, retirées sans savoir pourquoi).
- **Renvoyé à chaque appel** : chaque phrase occupe la fenêtre et s'ajoute au traitement. **Mise en cache** du début de séquence (fournisseurs) : réduit **coût et délai** si le début ne change pas, **pas la place** occupée.

## La boucle conversationnelle

- Le modèle ne retient rien ; le **programme conserve la liste des messages**. À chaque nouveau message :
  1. ajoute le message utilisateur à la liste ;
  2. soumet **la liste entière précédée du _system prompt_** ;
  3. reçoit la réponse, l'ajoute à la liste ;
  4. l'affiche, attend la suite (fig. 3-1 : « seule la liste conserve la conversation »).
- **Tour** : de l'arrivée d'un message utilisateur à la réponse rendue. Ici **1 appel au modèle par tour** ; plusieurs dès le ch. 4. Le modèle **relit toute la conversation** à chaque tour, comme s'il la découvrait.
- Tenir la liste = **choisir son contenu** : raccourcir, résumer, insérer une information. Le modèle répond sur la version présentée (état et contexte : ch. 8 à 10).

## L'historique se remplit

- La liste s'allonge à chaque tour → **volume, coût, latence** ↑ ; consignes initiales et infos anciennes **plus difficiles à exploiter** au milieu des messages.
- Fenêtre pleine → retirer des messages. Supprimer les **plus anciens** : simple, mais perte du début ; si l'interface ne le signale pas, l'utilisateur ignore que ses précisions sont devenues inaccessibles.
- **Fil rouge jusqu'au ch. 10** : rien n'est retiré ; dépassement de la fenêtre → **l'appel échoue, le tour finit en erreur**.
- Discret pour des questions brèves ; **central** dès plusieurs appels par demande.

## Transmission en continu (*streaming*)

- Envoyer la réponse à l'interface **à mesure** que les *tokens* sont produits. Temps total **identique**, mais lecture immédiate et activité visible → distinguer **attente normale et panne**.
- Contreparties : prévoir les **vérifications avant affichage** (mots lus impossibles à retirer) ; traiter l'**interruption** en cours de transmission.
- **Sur le terrain** : prévoir le *streaming* **dès la première version**, avant les fonctions métier ; l'ajouter tard oblige à revoir erreurs et interruptions.

## Le *harness*, programme qui entoure le modèle

- ***Harness*** (harnais) : **ensemble du code qui entoure le modèle** pour en faire un assistant puis un agent utilisable (« le programme » dans le livre).
- **Le modèle produit du texte** (réponse ; demande d'action dès ch. 4), **sans effet par lui-même**. **Le _harness_** compose l'entrée (consignes, historique ; plus tard outils et résultats), appelle, **interprète**, **exécute**, **contrôle**, transmet, **choisit ce que le modèle lira** ensuite.
- Capacités réelles **bornées** par ce que le *harness* accepte d'exécuter et place dans le contexte. **Frontière modèle / programme = question de conception de tout le livre.**

| Responsabilité (tab. 3-1) | Le *harness*… | Développé |
|---|---|---|
| **Composer l'entrée** | consignes + historique ; plus tard outils, résultats, infos | ici ; P. III ; P. IV |
| **Conduire le tour** | appelle le modèle, poursuit ou s'arrête | ici ; P. II |
| **Interpréter, exécuter** | lit, vérifie, exécute les demandes d'action | ch. 4 ; P. II |
| **Encadrer** | limites, droits, validations | ch. 7 ; ch. 14 |
| **Conserver l'état** | historique, besoins de la tâche | ici ; P. III |
| **Communiquer** | *streaming*, informer de ce que fait l'agent | ici ; P. II |

- Seuls existent : entrée, tour à **un appel**, historique, *streaming*. P. II boucle, capacités, droits ; P. III contexte ; P. IV ce qu'on y remet ; P. V éprouver, maintenir.
- Responsabilités = **code ordinaire**, spécifié et testé par le génie logiciel ; le **modèle s'évalue par observation** de ses sorties sur **exécutions répétées**.
- **Même modèle, deux équipes** : longue description + historique rejoué jusqu'à remplir la fenêtre (précisions perdues) vs consignes courtes + entrée **choisie à chaque tour** → comportements différents.
- Indices : l'**interface agent–environnement** modifie comportement et résultats (Yang et al., 2024, SWE-agent) ; évaluation des agents confondant besoins des **développeurs de modèles** et **constructeurs d'applications** (Kapoor et al., 2024).

## Sans outil, l'assistant ne peut pas…

- Assistant complet au sens simple : converse, reformule, explique, rédige. Mais ignore les **commandes**, même **la date du jour** ; explique une annulation sans pouvoir **la déclencher**.
- Enrichir le contexte (date, nom, extrait de doc) : utile si ciblé ; tout charger : impossible → **obtenir les données pertinentes au moment de la question** (ch. 4).

## Fil rouge : le premier *system prompt*

- Choix de conception de l'éditeur, **avant tout accès aux données** : que mettre dans le message système, et que sait faire l'assistant **avec cela seul** ?
- Options : **minimum** (rôle + public ; le modèle fait de son mieux) ; **documentation** (application, notions métier, écrans, pour guider l'utilisateur) ; **bornes** (ne jamais affirmer l'état d'une commande qu'il ne peut pas connaître).
- **Retenu** : prompt **court** — aide aux chargés de clientèle, périmètre limité aux **commandes**, réponses **brèves** dans la langue de l'utilisateur, **règle de prudence** : aucune information sur une commande précise **sans l'avoir obtenue d'une source**.
- Documentation **écartée** : allonge **chaque appel** pour un bénéfice incertain, à tenir à jour à chaque évolution des écrans.
- **Coût** : à « où en est la commande de tel client ? », il répond **ne pas disposer de l'information** — limite correctement exposée, service non rendu (il faudra consulter la commande). La règle reste **une consigne sans contrôle** : observer s'il la suit, surtout quand l'utilisateur **insiste**.

| Modèle | LLM généraliste, utilisé tel quel |
| Consignes | *system prompt* court : rôle, périmètre, registre, une règle |

## Pièges

- **Ajouter une ligne au _system prompt_ à chaque problème** → au bout de quelques mois, consignes qui **se contredisent**, et plus personne ne sait lesquelles sont utiles (sortie : ch. 13).
- **Secret** dans le prompt (restituable) ; consigne crue **garantie**.
- **Historique** : coût et latence croissants, consignes initiales noyées ; **troncature silencieuse** des plus anciens messages.
- ***Streaming*** : texte lu **irrévocable** → vérifier avant d'afficher ; gérer l'interruption ; l'ajouter tard coûte cher.
- **Zone d'incertitude** : *harness* vient de la pratique, **sans définition arrêtée** ; les travaux académiques décrivent un agent par ses composants — **mémoires, espace d'actions, procédure de décision** (Sumers et al., 2023). Définition = **convention du livre**.

## À retenir — chapitre

- Dialogue = convention : **messages attribués à des rôles**, que le modèle a appris à prolonger. **Priorité d'un rôle = comportement appris** : même séquence de *tokens*, **sans séparation étanche** entre consignes et autres contenus (sécurité : ch. 14).
- Le *system prompt* oriente chaque appel ; une règle impérative exige aussi un **contrôle dans le programme**.
- **Mémoire apparente** = historique que le programme **renvoie intégralement à chaque tour** ; c'est cette relecture qui fait tenir compte des messages précédents. Il grandit : il faudra un jour **en retirer**.
- Le *harness* compose l'entrée, appelle, interprète, exécute, contrôle, transmet : **les capacités réelles de l'agent dépendent de lui**.
- **Un résultat d'évaluation porte sur le couple modèle + _harness_** ; le classement d'un modèle sur un banc d'essai général ne suffit pas à prévoir votre assistant (mesure : ch. 15).
- Suite : le ch. 4 donne à l'assistant son **premier outil** — obtenir l'état réel d'une commande.
